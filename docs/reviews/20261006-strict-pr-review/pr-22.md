## Reproduced findings and fixes

### F22-01 - P2: DST makes History lose recorded work

Original new `activityDayKeys` lines 137-138 use `dayKey`, while `dayRange` builds local-clock boundaries. In America/New_York with `dayStartHour = 4`, work from 04:10 to 04:40 on 2026-03-08 yields only the key 2026-03-07. History's total is 0; engine focus and the correct `dayRange` total are 1,800,000 ms. On the fall transition date, 2026-11-01, work before the boundary is assigned to the later day. The preexisting elapsed-hour `dayKey` became a new conservation failure because the PR's History sums only enumerated daily ranges.

Fix: compare `ts` against that calendar day's local boundary; shift the local date only before it. Four new DST regressions failed before the fix (4 failed / 22 passed), then passed. Tests exercise actual timezone offsets of 240 and 300 minutes, pre-boundary, exact boundary, after-boundary, noon, touching days, week total, and an entirely after-boundary session.

### F22-02 - P2: an accepted timestamp outside Date's range freezes History

Original public `parseArgs('session:update')` and real `editSession` accepted finite values `startedAt = 1e20` and `endedAt = 1e20 + 1e6`. Both date keys become `NaN-NaN-NaN`; `shiftDay` repeats that key forever. A normal child process using the real source exited with code 0 and a date key; the malformed child printed before enumeration and timed out after 1,000 ms (`ETIMEDOUT` / `SIGTERM`). The timeout belonged only to the owned reproduction process. `Infinity` itself was rejected by the actual Zod contract and is not a claimed accepted input.

Fix: command timestamps constrained to Date's finite representable range; enumeration validates both dates and enforces advancing calendar keys. Persistence validation is coordinated with the PR #21 inventory owner. No session is deleted by the core guard.

### F22-03 - P2: a Date-valid long record crashes the all-days history

An interval from 1800-01-01 04:00 to 2400-01-01 04:00 is Date-valid and accepted. Actual `activityDayKeys` produced 219,145 days in 383 ms; History's `Math.max(1, ...totals)` call shape throws `RangeError: Maximum call stack size exceeded`. Enumerating and summarizing every date also scales with elapsed centuries on each renderer tick.

Fix: History explicitly selects a calendar month, clips enumeration before creating keys, and offers previous/next/current-month controls plus a direct month input. All-time total uses one full-extent `activitySummary`, not daily expansion; session objects and per-day/full-session distinction remain. The long-record regression returns 31 October dates while independently preserving monthly duration, whole duration, both raw endpoints and half-open zero-length inclusion.
