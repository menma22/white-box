# 決めたこと

仕様書 §23 で「未確定」としていた項目のうち、Phase 1 の実装で決めたもの。
**採らなかった選択肢も残す**——後から「なぜこうしなかったのか」を掘り直さずに済むように。

新しく判断したら、下の形式で1件足す。

---

## 001. デスクトップの土台に Electron を使う

**決定**: Electron 33。

**なぜ**: 仕様 §16 でデスクトップアプリは確定していて、残る候補は Tauri と Electron だった。Tauri は Rust と MSVC ビルドツールを要求し、開発環境に入っていなかった（数 GB の導入が前提になる）。UI は同じ Web 技術で書くので、必要になったら移せる。

**採らなかったもの**: Tauri（配布サイズは圧倒的に小さいが、着手コストが高い）。

---

## 002. 保存は JSON 1ファイル

**決定**: `data.json` 1ファイル + `backups/` に日次コピー30日ぶん。書き込みは一時ファイルを作ってから置き換える。

**なぜ**: SQLite（`better-sqlite3`）はネイティブビルドが要り、Windows で MSVC を前提にする。個人が数年使っても記録は数千件で、全部メモリに載る規模。1ファイルなら書き出し・移行・目視確認が全部ただのファイル操作で済み、仕様 §19（長期データ保全）と相性がいい。

**採らなかったもの**: SQLite。件数が桁違いになるか、部分読み込みが要るようになったら再考する。ファイルへの読み書きは保存層の `apps/desktop/src/infra/store.ts`（決定当時は `electron/store.ts`）に集約しているので、そのときの差し替え範囲は小さい。

---

## 003. タイマーはメインプロセスが持つ

**決定**: セッションの状態と1秒ごとの進行はメインプロセスが持ち、レンダラへは変化だけを配る。

**なぜ**: 仕様 1-10 に「× で閉じても計測は続く」がある。レンダラにタイマーを置くとウィンドウを閉じた瞬間に止まる。

---

## 004. 実作業時間は「経過 − 一時停止の重なり」で定義する

**決定**: `packages/core/src/engine.ts` の純関数だけがこの計算をする。区間（Task Segment）ごとの時間は、その区間に重なる停止だけを引く。

**なぜ**: 記録の正しさがこのアプリの全部なので、計算を1箇所に閉じてテストで固定する。区間ごとに按分しないと、タスク別の合計がセッションの合計と合わなくなる。

---

## 005. スリープ・画面ロックで自動的に一時停止する

**決定**: 既定で有効。設定で切れる。

**なぜ**: 離席した時間が実作業に化けると、仕様 §2「歪みなく記録する」が成立しない。仕様の Phase 1 には無い項目だが、記録の正しさそのものに関わるので入れた。

---

## 006. ショートカットは Ctrl+Alt+S / W / D を既定にし、設定で変えられるようにする

**決定**: 開始・一時停止・再開はすべて `Ctrl+Alt+S` の1つに集約。`Ctrl+Alt+W` で現在の仕事、`Ctrl+Alt+D` でメイン画面。設定画面でキーを押して録り直せる。

**なぜ**: 仕様 §23 で「キーは未確定」「Start と Pause を同じにするか未確定」となっていた。他のアプリとの衝突は環境ごとに違うので、値を決め打ちするより**変えられること**を先に用意した。1つに集約したのは 1-10 の「停止中に同じショートカットで確認なしで即再開」を素直に満たすため。

---

## 007. 書体は Windows 標準のみを使う

**決定**: Segoe UI Variable Display / Georgia / Yu Gothic UI。Web フォントを読み込まない。

**なぜ**: 完全ローカルのアプリで外部にフォントを取りに行くと、起動が遅くなり、オフラインで見た目が壊れ、外部通信が発生する。標準フォントの組み合わせでも十分に性格を出せる。

---

## 008. 配布物は自前で組み立てる

**決定**: `scripts/pack.mjs`（コピー + `rcedit`）を主経路にする。electron-builder は任意。

**なぜ**: electron-builder は `winCodeSign` の展開でシンボリックリンクを作り、開発者モードでない Windows では止まる。システム設定を変えずに配布物を作れる方を既定にした。

**採らなかったもの**: NSIS インストーラを既定にすること。

**※ 2026-08-23 訂正**: 当初ここには「アンインストーラや Add/Remove Programs への登録が欲しくなったら `npm run dist` を使う」と書いていたが、その逃げ道はもう無い。pnpm monorepo 化で `build.files` が `@white-box/core` / `@white-box/contracts` / `zod` を含まなくなり、`npm run dist` は「開発者モードを有効にすれば通る」どころか、通っても起動直後に `import` で落ちるインストーラを作る状態になった。`pack.mjs` 側だけが手で node_modules を組み立てており、electron-builder 側に同じ手当ては無い。動く顔をした壊れた経路を残さないため、`dist` スクリプトと `package.json` の `build` 設定を削除した。インストーラが要るようになったら、`pack.mjs` の成果物を包む形で作り直す（→ [packaging.md](packaging.md)）。

## 009. アプリ内で asar にまとめない

**決定**: `resources/app/` に平のファイルとして置く。

**なぜ**: 個人の道具として、中身をそのまま読めた方が確認と修正が速い。難読化に意味がない。

## 010. 呼びかけの名前は設定値にし、既定は空にする

**決定**: `settings.displayName`。空のときは名前なしで挨拶する。

**なぜ**: Welcome の文面に名前が要るが、既定値に特定の名前を埋めると、他の人が使ったときに他人の名前で呼ばれる。

## 011. ライセンスは MIT

**決定**: MIT。

**なぜ**: 個人の道具を公開するときの一般的な既定で、後から制限を強める方向にも緩める方向にも動きやすい。

---

## 012. バックエンドは TypeScript のまま（Quri 形式への再編でも Python は採らない）

**決定**: メインプロセス（バックエンド）は TS のまま。2026-08-21 まひろ選択。

**なぜ**: Electron の窓・トレイ・グローバルショートカットは Node.js でしか扱えず、Python を入れても消えない——横に 3 つ目のプロセス（サイドカー）が増えるだけ。TS 同士なら型を import で直接共有でき、Python なら必須になる codegen 工程そのものが不要。Python 実行環境の同梱は「動かすために環境に何も要求しない」という 001・002 以来の軸にも反する。

**採らなかったもの**: Python サイドカー（FastAPI）。Quri の実装パターンを流用できる利点より、配布と構成の複雑化が重い。

---

## 013. 契約は zod の TS スキーマで書く（OpenAPI YAML は採らない）

**決定**: `packages/contracts` に全コマンドの zod スキーマを置き、レンダラとメインの両方がこれを import する。まひろは「OpenAPI のように FE と BE がちゃんと分かれていればなんでもいい」と形式を委任（2026-08-21）——分離の実体は import 境界の機械強制（renderer → contracts/core のみ）で担保する。

**なぜ**: 通信が HTTP でなく IPC なので、OpenAPI の語彙（パス・メソッド・ステータスコード）が合わない。TS 同士なら定義＝型＝実行時検証が 1 箇所で一致し、生成工程も生成物の同期管理も要らない。

**採らなかったもの**: OpenAPI YAML + codegen（Quri と完全同形になる利点はあるが、上記の無理が出る）。

**決定**: Quri と同じ pnpm workspace 構成（apps/desktop・apps/renderer・packages/contracts・packages/core）。2026-08-21 まひろ選択。

**採らなかったもの**: 単一パッケージのまま層をフォルダで分ける案（移行は小さいが、パッケージ境界が物理的に固くならない）。

## 015. Storybook を導入する

**決定**: apps/renderer に Storybook を置き、「story 先行 → 確認 → 結線」の Quri 開発順序を使う。2026-08-21 まひろ選択。story には結果の状態だけを渡し、機構を写さない（fixture.ts と同じ規律）。

## 016. 再編は大きな Phase に分けて進め、最後まで完了させる

**決定**: [rebuild-plan.md](rebuild-plan.md) の Phase 0–5。複数セッション引き継ぎ前提で進めるが、途中で止めず完全に移行しきる（2026-08-21 まひろ指示「段階的でもいいし、大きなタスクごとに分けて計画は進めるべき。でも最後まで完全には移行しきるよ」）。

**なぜ**: どの時点でもアプリが動き日常使用できる状態を保つため（MVP は「毎日使う」フェーズに入っている）。大規模移行を 1 本に積むと検証不能になる。

---

## 017. 除外の申告は pauses の 'excluded' 区間で表し、契約は session:update の拡張にする

**決定**: 止め忘れ・満了後放置で実作業に化けた時間は、終了済みセッションの `pauses` に `reason: 'excluded'` の区間を後から足す形で申告する。契約は新コマンドではなく `session:update` の patch に `exclusions: TimeRange[]`（申告の全体を置き換え）を足す。観測された停止（manual/suspend/lock）には触れない。不正な申告（範囲外・重複・逆さま・未終了）は受け口で拒否する。

**なぜ**: 実作業 = 経過 − 一時停止の重なり（004）なので、pauses に足せば engine の純関数 1 本で正しく減る。`endedAt` を動かす案は「何時まで席にいたか」という起きた事実を消す（仕様の「過去を消さない」に反する）。除外の申告は「記録を手で直す」の一種なので、1 回の編集 = 1 つの editedAt = 1 件の session_edited に収まる既存コマンドの拡張が正しい。重複を拒否するのは親切ではなく計算の正しさのため（重なりは同じ時間を二重に引く）。

---

## 018. 満了後放置の除外導線は終了レビューに置く（満了ポップアップではなく）

**決定**: 超過分を実作業から外す 1 ボタンは ReviewWindow に置く。超過があったときだけ「予定を過ぎてから ◯ 動いたことになっている」バナーが出る。満了ポップアップは変更しない。

**なぜ**: レビューはどの終わり方でも必ず出る（満了ポップアップは、見逃した本人には出ていない）。終了済みセッションへの事後修正と同じコマンドが使え、`endSession` に「満了時点で閉じる」変種を増やさずに済む。押した結果（実作業が減る）がその場で見える。再検討条件: レビューを毎回飛ばして気づけない、となったとき（その場合もポップアップに増やすのではなく、履歴側の気づかせ方を強くする）。

---

## 019. ショートカットは既定空。初回オンボーディングで本人が割り当てる

**決定**: DEFAULT_SETTINGS のショートカットを空にし、初回起動時に 4 ステップ（歓迎 → 名前（任意）→ ショートカット割り当て → 完了）のオンボーディングで本人に割り当ててもらう（スキップ可）。既存 DB は「使った痕跡」（sessions / tasks / projects / dayNotes / shortcuts / displayName のいずれかが非空）があれば読み込み時にオンボーディング済み扱いにする。

**なぜ**: 既定 Control+Alt+S/W/D は他アプリと衝突し得る（実測では同一 PC の White Box 別インスタンスとすら衝突した）。ショートカットは「作業を中断せずに開始・停止できるか＝記録が残るか」を決めるので、初回に必ず 1 回通す価値がある。済み判定を「data.json の有無」にしないのは、入れて即終了した新規ユーザーにも既定ファイルが書かれるため。マイグレーション基盤は 1 項目のために作らない。

---

## 020. セッション中の HUD は表示専用の透過ミニカードにする

**決定**: HUD（248x88 の窓・212x44 のカード）は経過と残りだけを表示し、操作要素を持たない。クリックは `setIgnoreMouseEvents` で下へ素通り、カーソルが寄るとメインプロセスのカーソル監視（90ms）で最も遠い隅へ退く。消せるのは設定のトグル（`showSessionCard`）だけ。一時停止・終了はショートカットと「現在の仕事」画面が担う。

**なぜ**: セッション中の常時表示 UI は、作業への注意を奪わず「記録が動いていること」だけを見せるのが役目（アプリ内 todo 08-21・ダイナミックアイランド参照 08-29）。透過は `transparent: true` + ページの地を `insertCSS`（`!important` 必須）で消す方式。`backgroundMaterial: 'acrylic'` は窓の矩形全体にしか効かずピル型にできないため不採用。`backdrop-filter` は透過窓では窓の裏に届かないため不採用。逃げ判定をメインプロセスに置くのは、クリック透過の窓はレンダラでマウスを受け取れないため（契約変更なしで完結する副次効果もある）。

---

## 021. 道標は White Box の保存とタスクを共有する

**決定**: 目標・問題・構造履歴を Database の `goalMap` に追加し、タスクは既存の `tasks` を使う。画面は React と既存のデザイントークンで実装する。目標の木とタスクの親子関係は別に保ち、`goalNodeId` で関連付ける。

**なぜ**: 目標を分解した後の実行をボードと時間計測へつなぐため。目標の構造を変更しても、実行済みタスクやセッションの意味を変えない。

**採らなかったもの**: 旧アプリを iframe と localStorage のまま埋め込むこと。独立したタスク台帳・保存・バックアップが残り、同じ仕事の編集や完了が二重になるため。[機能対応と移行契約](michishirube.md)を参照。

---

## 022. 今日・週・履歴は日境界で切った同じ実作業区間を使う

**決定**: `packages/core/activity` が設定した日境界と月曜始まりの週で区間を切り、総時間・Project別・Task別・Session別・最近14日の値とTimelineへ同じ区間を返す。Sessionの先頭・末尾と満了上限は既存engineの `segmentRange` / `focusEndOrNow` を使う。翌日は暦で求め、24時間の固定加算にしない。

編集でSession同士が重なる場合は、開始時刻・ID・区間順が先の実作業へ一度だけ帰属させる。別Sessionの実作業がある瞬間は実作業を優先し、残りの停止は除外・タスク整理・その他の順に重複を解消する。この方針は記録を変更せず集計に適用する。日・週のSession行には範囲内の時間とSession全体を区別して表示する。

**なぜ**: 開始日にSession全体を置くと、日をまたぐ仕事が別の日へ移り、日別の和と週合計が一致しない。別々の画面で停止減算を再実装すると、同じ記録から違う実績が生まれる。削除されたTaskの時間は未所属として残し、現在の進捗や目標成果を時間から推定しない。

---

## 023. 待ち・見積・停滞は進捗と独立した判断根拠にする

**決定**: Blocked・必須先行・推奨先行・外部待ちをTaskの任意情報として保存する。必須先行はDoneだけが満たし、推奨先行は強制しない。削除された必須参照は明示解除まで残す。開始・切替・再開・Doing・復旧・自動再開・取込で同じ条件を使う。外部連絡と目標達成は自動化しない。

残作業と安全余裕はSession Durationから独立し、空欄と0を区別する。Slackは締切日の翌日0時までの暦時間から両方を引き、欠損は不明。AgingはTodoだけで、現在のコミット・実進捗・engineの実作業を起点にする。旧作成日で補わず、メモや停止でリセットしない。設定の閾値でWarning、2倍でHigh Risk、負のSlackでHigh Risk、締切超過でOverdueを示す。

保存は通常の変更を巻き戻す。取込が既に保存された後、実行不能なSessionの復旧停止を保存できない場合だけ、未保存の安全停止をメモリと表示に維持する。Windowsの一時的なrename失敗はエラー種類・回数・時間を限定して再試行し、直接上書きや宛先削除で回避しない。

**なぜ**: 70%進んだ仕事にも待ちがあり、見積の欠損を0扱いすると余裕を捏造する。実作業と関係のない更新で停滞を消すと次の行動を考える根拠が失われる。警告からも既存の開始条件を守り、本人が待ち・先行・重要度・Inboxへの戻しを整理できるようにする。

---

## 024. 週の配分・外部固定予定・再開の文脈を必要な場面で編集する

**決定**: 週予算は暦の月曜0時からの168時間を基準とし、睡眠・食事・その他の固定時間・外部固定予定の重複を除いた時間を控除する。残った柔軟な時間をProjectへ最小・最大・範囲・上限なしで配分し、既定配分を再利用できる。生活時間の空欄を推定値で埋めない。Weekは実績を先に表示し、予算を開いたときだけ編集する。

Fixed Workは既存Taskに外部の理由と未来の開始・終了を登録する。予定登録はSessionや作業開始を生成しない。重複する予定は資源控除で一度だけ数える。Project Priorityは既存の低・普通・重要を使い、旧データの未設定を保持する。Taskの重要度と独立した判断材料として候補順位へ加える。

Taskの既存`notes`に`problems`・`decisions`・`nextContext`を任意追加する。本人が選んだ一種類だけを編集し、長文は既存のlinked Noteへ残す。Next ContextはStart/Current Workで参照できる。Taskやタブを移る前に保存を待ち、失敗時は入力と画面を保持する。週予算の保存前入力はMain内で週・タブを移っても保持する。

複数窓のTask名・文脈・Noteは、変更する項目の保存済み期待値を受け口で照合する。別項目の更新は妨げず、同じ項目の競合は両方の文章を表示して自動保存を止め、本人が明示的に選択する。入力の保存待ちから画面切替完了まで操作を固定する。Task名の空欄入力は従来どおり保存済みの名前へ戻すが、意味のある入力の保存失敗を空欄取消と扱わない。

**なぜ**: 配分計画と実作業の履歴を混ぜると、時間を確保しただけで実行したように見える。常時すべての入力欄を並べると、仕事より情報管理の負担が増える。再開に必要な内容を、その仕事へ戻る場面で取り出せるようにする。

Blocked理由は未保存の入力を保持し、外部待ちは本人が登録した保存の完了を待つ。登録失敗が残る間はclose/switch/quitを拒否し、再試行または本人の取消を待つ。未登録の外部待ちフォームを移動時に勝手に登録しない。

## 025. 終了前の保存を成功させてからサービスを停止する

**決定**: トレイ・別の窓・native closeを含む終了・切替は、入力のあるrendererの保存応答を先に待つ。読み込み中の窓も準備完了と保存応答を待つ対象に含める。送信元とrequest IDを照合し、成功応答後も移動・終了が完了するまで入力を固定する。保存失敗・無応答時は操作を取り消す。終了準備中は新しい窓や作業を始めず、既存の下書きの保存を通す。アプリ終了前に生存記録とDBを保存し、失敗時は終了を取り消してエラーを表示する。失敗した段階ではticker等のサービスを停止しない。保存成功後は終了状態により満了・復元・wake・ticker開始・遅れて来た変更コマンドも止める。

休憩の自動再開と復旧は終了準備中から停止する。native closeは保存確認の開始前と応答後に終了準備との競合を再検査し、競合時は窓を維持して入力ロックを解除する。先に開いた読み込みダイアログも、選択・確認の応答後に終了状態を確認してからDBを置き換える。停止済みのAI連携サービスに起動失敗が遅れて届いても、設定やDBを変更しない。

遅延closeは予約時のBrowserWindowだけへ送る。MainとCurrentの初回表示は `ready-to-show` と `did-finish-load` のうち先に届いた通知で一度だけ行い、読み込み完了後に非表示のまま残る経路を防ぐ。終了準備中や破棄済みの窓は表示しない。

**なぜ**: 保存失敗後に終了すると未保存の情報が失われる。終了中に新しい窓や自動再開が発生すると終了の対象が増える。過去の15秒QUIT停止のnative原因は未確定であり、この修正の検証と原因解決の断定を分ける。
