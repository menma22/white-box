# 決めたこと

仕様書 §23 で「未確定」としていた項目のうち、Phase 1 の実装で決めたもの。
**採らなかった選択肢も残す**——後から「なぜこうしなかったのか」を掘り直さずに済むように。

新しく判断したら、下の形式で1件足す。

---

## 001. デスクトップの土台に Electron を使う

**決定**: Electron 33。

**なぜ**: 仕様 §16 でデスクトップアプリは確定していて、残る候補は Tauri と Electron だった。Tauri は Rust と MSVC ビルドツールを要求し、開発環境に入っていなかった（数 GB の導入が前提になる）。UI は同じ Web 技術で書くので、必要になったら移せる。

**採らなかったもの**: Tauri（配布サイズは圧倒的に小さいが、着手コストが高い）。

---

## 002. 保存は JSON 1ファイル

**決定**: `data.json` 1ファイル + `backups/` に日次コピー30日ぶん。書き込みは一時ファイルを作ってから置き換える。

**なぜ**: SQLite（`better-sqlite3`）はネイティブビルドが要り、Windows で MSVC を前提にする。個人が数年使っても記録は数千件で、全部メモリに載る規模。1ファイルなら書き出し・移行・目視確認が全部ただのファイル操作で済み、仕様 §19（長期データ保全）と相性がいい。

**採らなかったもの**: SQLite。件数が桁違いになるか、部分読み込みが要るようになったら再考する。データを触るのは `electron/store.ts` だけなので、そのときの差し替え範囲は小さい。

---

## 003. タイマーはメインプロセスが持つ

**決定**: セッションの状態と1秒ごとの進行はメインプロセスが持ち、レンダラへは変化だけを配る。

**なぜ**: 仕様 1-10 に「× で閉じても計測は続く」がある。レンダラにタイマーを置くとウィンドウを閉じた瞬間に止まる。

---

## 004. 実作業時間は「経過 − 一時停止の重なり」で定義する

**決定**: `shared/engine.ts` の純関数だけがこの計算をする。区間（Task Segment）ごとの時間は、その区間に重なる停止だけを引く。

**なぜ**: 記録の正しさがこのアプリの全部なので、計算を1箇所に閉じてテストで固定する。区間ごとに按分しないと、タスク別の合計がセッションの合計と合わなくなる。

---

## 005. スリープ・画面ロックで自動的に一時停止する

**決定**: 既定で有効。設定で切れる。

**なぜ**: 離席した時間が実作業に化けると、仕様 §2「歪みなく記録する」が成立しない。仕様の Phase 1 には無い項目だが、記録の正しさそのものに関わるので入れた。

---

## 006. ショートカットは Ctrl+Alt+S / W / D を既定にし、設定で変えられるようにする

**決定**: 開始・一時停止・再開はすべて `Ctrl+Alt+S` の1つに集約。`Ctrl+Alt+W` で現在の仕事、`Ctrl+Alt+D` でメイン画面。設定画面でキーを押して録り直せる。

**なぜ**: 仕様 §23 で「キーは未確定」「Start と Pause を同じにするか未確定」となっていた。他のアプリとの衝突は環境ごとに違うので、値を決め打ちするより**変えられること**を先に用意した。1つに集約したのは 1-10 の「停止中に同じショートカットで確認なしで即再開」を素直に満たすため。

---

## 007. 書体は Windows 標準のみを使う

**決定**: Segoe UI Variable Display / Georgia / Yu Gothic UI。Web フォントを読み込まない。

**なぜ**: 完全ローカルのアプリで外部にフォントを取りに行くと、起動が遅くなり、オフラインで見た目が壊れ、外部通信が発生する。標準フォントの組み合わせでも十分に性格を出せる。

---

## 008. 配布物は自前で組み立てる

**決定**: `scripts/pack.mjs`（コピー + `rcedit`）を主経路にする。electron-builder は任意。

**なぜ**: electron-builder は `winCodeSign` の展開でシンボリックリンクを作り、開発者モードでない Windows では止まる。システム設定を変えずに配布物を作れる方を既定にした。

**採らなかったもの**: NSIS インストーラを既定にすること。アンインストーラや Add/Remove Programs への登録が欲しくなったら `npm run dist` を使う。

---

## 009. アプリ内で asar にまとめない

**決定**: `resources/app/` に平のファイルとして置く。

**なぜ**: 個人の道具として、中身をそのまま読めた方が確認と修正が速い。難読化に意味がない。

---

## 010. 呼びかけの名前は設定値にし、既定は空にする

**決定**: `settings.displayName`。空のときは名前なしで挨拶する。

**なぜ**: Welcome の文面に名前が要るが、既定値に特定の名前を埋めると、他の人が使ったときに他人の名前で呼ばれる。

---

## 011. ライセンスは MIT

**決定**: MIT。

**なぜ**: 個人の道具を公開するときの一般的な既定で、後から制限を強める方向にも緩める方向にも動きやすい。

---

## 012. バックエンドは TypeScript のまま（Quri 形式への再編でも Python は採らない）

**決定**: メインプロセス（バックエンド）は TS のまま。2026-08-21 まひろ選択。

**なぜ**: Electron の窓・トレイ・グローバルショートカットは Node.js でしか扱えず、Python を入れても消えない——横に 3 つ目のプロセス（サイドカー）が増えるだけ。TS 同士なら型を import で直接共有でき、Python なら必須になる codegen 工程そのものが不要。Python 実行環境の同梱は「動かすために環境に何も要求しない」という 001・002 以来の軸にも反する。

**採らなかったもの**: Python サイドカー（FastAPI）。Quri の実装パターンを流用できる利点より、配布と構成の複雑化が重い。

---

## 013. 契約は zod の TS スキーマで書く（OpenAPI YAML は採らない）

**決定**: `packages/contracts` に全コマンドの zod スキーマを置き、レンダラとメインの両方がこれを import する。まひろは「OpenAPI のように FE と BE がちゃんと分かれていればなんでもいい」と形式を委任（2026-08-21）——分離の実体は import 境界の機械強制（renderer → contracts/core のみ）で担保する。

**なぜ**: 通信が HTTP でなく IPC なので、OpenAPI の語彙（パス・メソッド・ステータスコード）が合わない。TS 同士なら定義＝型＝実行時検証が 1 箇所で一致し、生成工程も生成物の同期管理も要らない。

**採らなかったもの**: OpenAPI YAML + codegen（Quri と完全同形になる利点はあるが、上記の無理が出る）。

---

## 014. pnpm monorepo にする

**決定**: Quri と同じ pnpm workspace 構成（apps/desktop・apps/renderer・packages/contracts・packages/core）。2026-08-21 まひろ選択。

**採らなかったもの**: 単一パッケージのまま層をフォルダで分ける案（移行は小さいが、パッケージ境界が物理的に固くならない）。

---

## 015. Storybook を導入する

**決定**: apps/renderer に Storybook を置き、「story 先行 → 確認 → 結線」の Quri 開発順序を使う。2026-08-21 まひろ選択。story には結果の状態だけを渡し、機構を写さない（fixture.ts と同じ規律）。

---

## 016. 再編は大きな Phase に分けて進め、最後まで完了させる

**決定**: [rebuild-plan.md](rebuild-plan.md) の Phase 0–5。複数セッション引き継ぎ前提で進めるが、途中で止めず完全に移行しきる（2026-08-21 まひろ指示「段階的でもいいし、大きなタスクごとに分けて計画は進めるべき。でも最後まで完全には移行しきるよ」）。

**なぜ**: どの時点でもアプリが動き日常使用できる状態を保つため（MVP は「毎日使う」フェーズに入っている）。大規模移行を 1 本に積むと検証不能になる。
