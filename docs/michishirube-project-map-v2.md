# 道標のプロジェクトマップ構想 v2

版: v2（2026-10-14）。前版: [v1](michishirube-project-map-v1.md)。変更: 本人発言の出典・日付を訂正し、原文を確認できない付箋UIの引用を設計提案へ戻した。状態: **実使用から生まれた構想案**。既存機能の仕様や実装済みの宣言ではない。

## 結論

道標のマインドマップを、**常時見えるマイルストーンの道筋**として使う。親子関係とは別にマイルストーン間の前提を結び、ひとつにフォーカスしたときだけ、その地点の問題・行動・解決策の候補を付箋として広げる。候補を検討して採用した後、既存のタスクやマップ上の到達点につなぐ。これにより、全体の進捗と次の行動を同じ場所から辿れるようにする。

この文書は、まひろが実使用で発見した課題と希望、ルーカスの設計提案、未決事項を区別して保存する。正式な実装要件は、検証・決定後に [product-spec.md](product-spec.md) へ反映する。

## 2. 現行仕様との境界

- [道標の統合仕様](michishirube.md)には目標の木、目標に関連するタスク・問題、成果物と達成結果がある。
- [成功条件のstory](stories/20261004_story_goal-criteria.md)では、測定・観測できる条件を目標に付け、目標の達成判定とは独立に扱う。
- [product-spec.md](product-spec.md)の `Hard Dependency` と `Recommended Order` はタスク管理の機能として記述され、[依存関係のstory](stories/20261005_story_dependencies-and-external-follow-up.md)で実装・検証されている。今回の論点は**目標・マイルストーン間の関係**であり、タスク間の依存をそのまま目標へ読み替えない。
- `Milestone` を独立したデータ型にするかは [product-spec.md](product-spec.md)で未確定。以下の「マイルストーン」はまずUI上の到達点という意味で用い、既存の `GoalNode` と別オブジェクトにすることは決めない。

## 3. 提案する情報構造

### 全体に常時見せるもの

マップの主役は、成果や判断可能な状態を表す**到達点**。最上位の目的、その内訳、到達点同士の前提、現在の判定を示す。作業メモや候補案は全体表示へ常時展開しない。到達点には「何をもって達成とするか」「結果・証拠への参照」「まだ分からないこと」を持たせる。

マップ上の線は最低限、次の意味を区別する。

| 関係 | 読み方 | 状態 |
| --- | --- | --- |
| 親子 | B は A の内訳 | 現行の中心構造 |
| 前提 `A → B` | A が満たされるまで B には進めない | 本人が実使用で必要性を確認した追加関係 |
| 寄与 `A → B` | A は B の達成に役立つが、それだけで B を保証しない | 設計提案。必要な実例で検証する |
| 条件分岐 | 結果が X なら A、Y なら B へ進む | 研究での利用を想定した設計提案。操作方法は未決 |

「A の後に B をするのが好ましい」だけなら強制的な前提線にしない。実行不能な関係と、推奨する順番を区別する。前提線が循環すると進めなくなるため、循環を検出する。研究上の反復は、偽の前提循環として表すのではなく、判断の結果を受けた再検討・次の試行として扱う。

子の到達点がすべて必要か、いくつかの代替経路があるかも、いずれは表現が要る。ただし親子線だけから親の達成を自動判定しない。達成は結果と成功条件を確認して決める。

### フォーカスしたときに開くもの

到達点を選ぶと、その周辺に**発散用の付箋**を開く。付箋には解決策、試したい方法、次の行動、障害、問いを素早く書ける。入力時には分類や評価項目を強制しない。付箋は選択した到達点に紐づくため、全体マップを閉じても考えた案は残る。

| 段階 | できること | マップへの影響 |
| --- | --- | --- |
| 発散 | 付箋を連続して書き出す | 全体表示の道筋を変えない |
| 整理 | 似た案をまとめ、期待効果・制約・確かめ方を必要に応じて比べる | 候補は候補のまま |
| 採用 | 案を既存の Task、到達点、問題・問いのいずれかへつなぐ | 実行する道筋として表示する |
| 保留 | 採らなかった案と理由を畳んで残す | 後の結果を受けて再検討できる |

**候補の付箋と、実行を約束した Task は別の状態**。付箋を書いただけでタスクや目標達成率を増やさない。採用時には同じ仕事の台帳を二重に作らず、[既存の Task と目標の関連](michishirube.md#タスクと目標の関係)へ接続する。これが具体的に「変換」か「リンク」かは未決。

### 到達点の判定と全体進捗

「作業した量」「タスクを終えた数」「目標に到達した証拠」を混ぜない。全体からは、達成を確認した到達点、いま着手できる行動、待っている前提、未解決の問いを別々に辿れるようにする。研究の結果が仮説を支持しなくても、「有効性を判定する」という到達点を達成した可能性がある。到達点の文言と判定条件が、その違いを決める。

未知の結果を事前に完全把握することはできない。「未判定」「方法未定」「仮定が未検証」を明示し、結果に応じてマップを更新できることを、実用上の可視化と制御の条件とする。

## 4. UIの利用例

1. 通常表示には「研究結果を判断できる」という親の下に、「評価条件を確定」「ベースラインを再現」「提案法を評価」を兄弟として並べる。
2. 「評価条件を確定 → ベースラインを再現 → 提案法を評価」に前提線を引く。親子関係を偽の直列構造に変えない。
3. 「提案法を評価」を選ぶと、その到達点の周囲だけに「追加データを集める」「別の指標を試す」「比較手法を増やす」などの付箋を表示する。選択を外すと付箋を畳み、マップの全体像へ戻る。
4. 案を選んだら、必要な作業は既存のボードの Task に結び、判断に必要な成功条件・証拠は到達点に記録する。案を選べないなら問いとして残す。

これは操作感を検討するための例で、画面配置、付箋の形、線の描き方は未決。

## 5. この案を試すときの確認条件

1. 同じ親の子 1・2・3 を並べたまま、1→2→3 の必須順を表せる。
2. 全体表示では到達点と重要な前提が読め、候補付箋の数が増えても全体の道筋を覆わない。
3. 目標へフォーカスすると紐づく案を再発見でき、フォーカスを外しても案は失われない。
4. 未採用の案は実行予定・達成済みとして数えない。採用時には既存の Task と重複しない。
5. タスク完了や成功条件への数値到達だけで、目標の達成判定を勝手に変えない。
6. 結果が予想と異なった場合も、仮説の非達成と「問いに答えられた」ことを区別して次の道を選べる。

## 6. 未決事項

- マップに常時出す「マイルストーン」を、既存 `GoalNode` の役割として扱うか、独立した型にするか。
- 前提線を目標間だけに張るか、Task との間にも張るか。タスクの `Hard Dependency` とどう整合させるか。
- 寄与・条件分岐・AND/OR の達成経路を、どの実例が必要とするか。最初から全種類を操作画面へ出すか。
- 付箋と既存の問題・問い・改善、Task のデータをどう共有し、採用・保留の履歴をどう保持するか。
- 線や付箋が多い場合の配置、フォーカスの範囲、キーボード操作をどう設計するか。
- 目標の達成判定と、前提を満たした結果としての「着手可能」をどう区別して表示するか。

これらが決まるまでは、本書を実装済み仕様や開発着手の承認と読まない。
